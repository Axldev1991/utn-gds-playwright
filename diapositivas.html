Bloque 1: Fundamentos Teóricos — Axel Castellano

Las 6 Dimensiones Ontológicas de Playwright

Indagación filosófica y técnica sobre la naturaleza y propósito del framework

1. ¿Qué es?
Framework moderno de automatización web y testing End-to-End (E2E) de código abierto desarrollado por Microsoft.
  • API unificada (TypeScript, Python, Java, C#).
  • Soporte nativo en Chromium, Firefox y WebKit.
2. ¿Para qué sirve?
Para simular con fidelidad las acciones reales de un usuario en la aplicación:
  • Validar flujos de negocio completos.
  • Prevenir regresiones funcionales en CI/CD.
  • Testing cross-browser y auditoría de accesibilidad.
3. ¿Por qué surge?
La web evolucionó hacia SPAs hiper-reactivas (Virtual DOM, micro-animaciones).
  • Selenium sufría de Flakiness por problemas de sincronización temporal.
  • Playwright surge para eliminar los fallos intermitentes desde el motor del browser.
4. ¿Cuál es su Objetivo?
Lograr suites de pruebas rápidas, deterministas y 100% confiables (Zero-Flakiness).
  • Eliminación total de pausas artificiales (sleep).
  • Ejecución paralela masiva sin colapsar la RAM.
5. ¿Cómo funciona?
Conexión bidireccional única por WebSockets directa con las APIs de depuración nativas:
  • Chrome DevTools Protocol (CDP) en Chromium.
  • Escucha eventos nativos en lugar de sondeo HTTP ciego.
6. ¿Cuándo usarlo y cuándo no?
  • SÍ: Flujos críticos de negocio, SPAs complejas, multi-tab y red.
  • NO: Pruebas unitarias de funciones puras (para esto usar Vitest o Jest en Node sin levantar browsers).
Bloque 1: Arquitectura de Software — Axel Castellano

Comparativa Arquitectónica: Protocolos y Procesos

Selenium WebDriver vs Cypress vs Microsoft Playwright

Selenium WebDriver
Arquitectura de 3 Capas (HTTP REST)
[Test Script]
  ↓ HTTP Request por comando
[chromedriver.exe]
  ↓ HTTP / W3C Wire
[Browser Process]

Alta sobrecarga de latencia acumulada y sondeo ciego (polling).

Cypress
In-Browser Runner (Iframe)
[Browser Window]
  └─ [Iframe Sandbox]
      ├─ [Test Script JS]
      └─ [Application JS]

Atrapado en el hilo de la app: sin multi-pestaña real y soporte WebKit limitado.

Microsoft Playwright
Out-of-Process (WebSocket Nativo)
[Test Script]
  ↕ Único WebSocket Bidireccional
[Browser Engine (CDP / DevTools)]

Eventos en tiempo real, control de red a nivel socket y velocidad extrema.

Jerarquía de Procesos en Playwright: Browser (Proceso pesado del SO) ➔ BrowserContext (Perfil efímero en <10ms con cookies y storage aislados) ➔ Page (Pestaña)
Aislamiento 100% Determinista
Bloque 4: QA Adaptativo & Resiliencia — Nicolás Rumie

Fragilidad de Selectores vs QA Adaptativo

Árbol DOM Interno vs Árbol de Accesibilidad (Accessibility Tree)

❌ Enfoque Tradicional Frágil (DOM Interno)
  • Acoplado a detalles de implementación: IDs sintéticos (#btn-create-task), clases de Tailwind o rutas XPath rígidas (//div[2]/button).
  • El problema industrial: Hasta un 60% del tiempo de QA se pierde reparando tests rotos por cambios cosméticos del frontend.
  • Comportamiento en UI v2: El botón muta a #act_btn_new_item_99f ➔ Colapso inmediato por TimeoutError.
// Roto en UI v2:
await page.locator('#btn-create-task').click();
✅ Enfoque de QA Adaptativo (Árbol A11y)
  • Acoplado a la intención del usuario: Utiliza roles ARIA y nombres accesibles que el navegador expone para lectores de pantalla.
  • Inmunidad ante refactors visuales: Las clases o IDs pueden cambiar completamente, pero el elemento sigue siendo un button con texto "Crear Tarea".
  • Comportamiento en UI v2: Pasa al 100% en ambas versiones de la interfaz sin modificar una línea de código.
// Resiliente en UI v1 y v2:
await page.getByRole('button', { name: /Crear Tarea/i }).click();
Bloque 4: Conclusiones y Cierre — Nicolás Rumie

Conclusiones del Proyecto y Cierre Técnico

Los cuatro pilares de la ingeniería de pruebas moderna demostrados en TaskFlow

1. Arquitectura de Software
Aplicación estricta de SRP y Page Object Model. Desacoplamiento de localización, infraestructura con Fixtures (IoC) y especificaciones BDD.
2. Sincronización Determinista
Erradicación total de pausas artificiales (sleep) mediante los 5 Actionability Checks de Playwright y Web-First Assertions.
3. QA Adaptativo & Self-Healing (IA)
Pruebas semánticas inmunes a rediseños y agente autónomo de IA capaz de diagnosticar fallos y autoreparar selectores con 98% de confianza.
4. Observabilidad Total
Diagnóstico avanzado con Trace Viewer: Time-travel debugging, snapshots interactivos del DOM antes y después de cada acción, y auditoría de red.
