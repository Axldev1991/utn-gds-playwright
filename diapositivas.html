Las 6 Dimensiones Ontológicas de Playwright

Fundamentación filosófica y técnica sobre el origen y propósito del framework

1. ¿Qué es?
Framework de testing y automatización E2E de código abierto desarrollado por Microsoft. Controla navegadores reales de forma programática mediante una API unificada y fuertemente tipada.
2. ¿Para qué sirve?
Validar flujos funcionales completos desde la perspectiva del usuario real, garantizando integridad en regresión, accesibilidad y rendimiento en múltiples resoluciones.
3. ¿Por qué surge? (Flakiness)
Viene a resolver la crisis de intermitencia (flakiness) de Selenium en SPAs modernas: tests que fallan por falta de sincronización temporal y no por bugs de código.
4. ¿Cuál es su Objetivo?
Garantizar ejecuciones deterministas y de alta velocidad en pipelines de CI/CD, eliminando esperas arbitrarias mediante sincronización nativa en el motor del navegador.
5. ¿Cómo funciona?
Utiliza una conexión WebSocket bidireccional persistente directo al navegador (Chrome DevTools Protocol - CDP en Chromium y protocolos equivalentes en WebKit/Firefox).
6. ¿Cuándo utilizarlo?
Ideal para SPAs complejas y reactivas con actualización asincrónica del DOM, flujos multi-pestaña, autenticación persistente y requerimientos de soporte cross-browser estricto.

Comparativa Arquitectónica: Protocolos y Procesos

Selenium WebDriver vs Cypress vs Microsoft Playwright

Dimensión Arquitectónica Selenium WebDriver Cypress Microsoft Playwright
Capa de Comunicación HTTP REST W3C mediante drivers externos (chromedriver, geckodriver) In-browser: corre dentro del mismo hilo del navegador en un <iframe> WebSocket directo (CDP) fuera de proceso
Mecanismo de Espera Manual / Explícita (WebDriverWait, sleeps) Retry-ability encadenado en comandos internos Auto-waiting determinista nativo en Locators
Navegadores Soportados Chrome, Firefox, Edge, Safari (Drivers separados) Chrome, Edge, Firefox (WebKit experimental) Chromium, Firefox y WebKit nativos en un solo API
Aislamiento de Tests Lento: nueva ventana o reinicio de browser completo Limpia cookies/storage pero comparte la misma ventana BrowserContext ultrarrápido (< 10ms) tipo incógnito
Observabilidad & Debug Logs de consola estáticos y capturas tras fallo Time-travel runner interactivo Trace Viewer paso a paso, DOM snapshots y red
💡 Conclusión Arquitectónica: Playwright combina la libertad del control fuera de proceso de Selenium con la sincronización y experiencia moderna de Cypress, superando las limitaciones de ambos.

Los 3 Desafíos Críticos del Testing en SPAs

Por qué las pruebas tradicionales colapsan ante el dinamismo del frontend moderno

1. Selectores Frágiles

El DOM cambia constantemente de maquetación por frameworks (React, Tailwind). Apuntarse a jerarquías CSS o IDs dinámicos rompe la prueba ante cualquier cambio estético.

// FRÁGIL (Roto ante cambios):
page.locator('div > div:nth-child(2) > button')
2. Contenido Asincrónico

Peticiones a APIs con latencia variable. Las esperas fijas artificiales generan lentitud o fallos aleatorios si el servidor demora 100 ms más de lo previsto.

// ANTIPATRÓN CATASTRÓFICO:
await page.waitForTimeout(2000);
3. Rutas Client-Side

La navegación no genera recarga completa de página (window.location), sino mutaciones de componentes vía la API History.pushState.

// No hay evento 'load' tradicional
SPA actualiza vista reactivamente en cliente

La SPA TaskFlow: Banco de Pruebas Reactivo

Desarrollo a medida con React 18, Vite y TypeScript bajo Principio de Responsabilidad Única

📦 Arquitectura de la SPA (Clean UI)
  • Desacoplamiento Estricto: React 18, Vite y TypeScript con servicios simulados y latencia asincrónica real (300-600ms).
  • Búsqueda con Debounce: Entrada reactiva con retardo de 300ms antes de mutar el DOM para evaluar sincronización determinista.
  • Modal y Toasts: Diálogos y notificaciones accesibles con atributos semánticos role="status".
  • Control de Sesión: Manejo de autenticación en memoria y LocalStorage con validación de rutas privadas.
🎛️ Módulo de QA Adaptativo: Toggle v1 vs v2

La aplicación incluye un interruptor en el encabezado para simular en tiempo real una mutación hostil de la interfaz:

• Modo UI v1: Clases e IDs estándar (ej. #btn-create-task).
• Modo UI v2: IDs dinámicos ofuscados (ej. #act_btn_new_item_99f), manteniendo intacto el árbol de accesibilidad semántica.

🎯 Permite demostrar empíricamente el quiebre de selectores CSS frente a la estabilidad del árbol accesible.

🚀 Demostración Práctica en Vivo: Probar login, debounce y switch UI v1/v2 a pantalla completa.
Bloque 2 • Sincronización Web-First

Sincronización Determinista vs. Esperas Ciegas

Cómo el motor de Auto-waiting y Web-First Assertions erradican el Flakiness

❌ Antipatrón de Esperas Fijas

Asumir tiempos mediante sleeps artificiales:

await page.click('#btn-submit');
await page.waitForTimeout(3000); // ¡Pausa ciega!
await page.click('#item');
  • Retrasa innecesariamente las suites en pipelines.
  • Falla aleatoriamente si la red demora 3001 ms.
✔️ Auto-waiting & Web-First Assertions

Sincronización reactiva contra el estado real de la UI:

// Espera determinista que resuelve en el milisegundo exacto:
await expect(page.getByRole('status'))
  .toHaveText('Tarea creada exitosamente');
  • Verifica que el elemento esté visible, habilitado y estable.
  • Ejecución a máxima velocidad y 100% determinista.

Arquitectura Page Object Model (POM)

Centralización de selectores semánticos y desacoplamiento de la lógica de negocio

BasePage
Clase base abstracta. Encapsula la instancia de page, métodos de navegación genéricos y helpers de accesibilidad global.
LoginPage
Encapsula los campos de email, password, botón de inicio de sesión y validación de alertas de error con getByRole('alert').
DashboardPage
Centraliza el header, el buscador reactivo, el filtro de estados de sprint, el contador de tareas y la apertura del modal.
TaskModalComponent
Componente reutilizable. Modela el formulario emergente (título, descripción, prioridad, asignado y confirmación).
🎯 Regla de Oro Aplicada: Los tests solo describen la intención de negocio (¿Qué se prueba?). Las clases POM resuelven la interacción técnica con el DOM (¿Cómo se interactúa?).

Fixtures e Inyección de Dependencias

Inspección interactiva del desacoplamiento entre Page Objects, Fixtures y Tests BDD

Extensión del runner de Playwright inyectando authenticatedPage e instancias POM con aislamiento estricto:
export const test = baseTest.extend<CustomFixtures>({
  dashboardPage: async ({ page }, use) => {
    const dashboard = new DashboardPage(page);
    await use(dashboard);
  },
  authenticatedPage: async ({ page }, use) => {
    // Login programático una única vez sin repetir formulario
    await loginPage.login('admin@taskflow.dev', 'password123');
    await use(page);
  }
});
Encapsulación del DOM en LoginPage utilizando selectores semánticos basados en el árbol de accesibilidad:
export class LoginPage extends BasePage {
  readonly emailInput: Locator;
  readonly submitButton: Locator;

  constructor(page: Page) {
    super(page);
    this.emailInput = page.getByLabel('Correo Electrónico');
    this.submitButton = page.getByRole('button', { name: /Iniciar Sesión/i });
  }
}
Test declarativo de alta de tareas recibiendo dashboardPage ya autenticado sin instanciaciones manuales:
test('3.1 Creación exitosa de tarea muestra Toast', async ({ dashboardPage }) => {
  const modal = await dashboardPage.openNewTaskModal();
  await modal.createTask({ title: 'Tarea E2E', priority: 'alta', assignee: 'Axel Castellano' });

  await expect(dashboardPage.toastNotification).toBeVisible();
  await expect(dashboardPage.getTaskCardByTitle('Tarea E2E')).toBeVisible();
});

Expositor: Nicolás Rumie

Experimento de QA Adaptativo: Toggle UI v1 vs. v2

Demostración empírica de quiebre de selectores CSS vs estabilidad semántica

💥 El Quiebre en UI v2 (fragile-selectors.spec.ts)

El test se acoplaba al ID del botón en versión 1:

await page.locator('#btn-create-task').click();

En Modo v2, el desarrollador refactorizó el botón a:

<button id="act_btn_new_item_99f" aria-label="Crear Tarea">
  <span>➕ Crear Tarea</span>
</button>

Resultado: TimeoutError 5000ms. La suite de CI/CD se tiñe de rojo sin que haya un bug funcional.

🛡️ Resiliencia Semántica (adaptive-semantic.spec.ts)

La prueba implementada con el árbol de accesibilidad (A11y):

await page.getByRole('button', { name: /Crear Tarea/i }).click();
  • Inmune a mutaciones: El ID cambió pero el rol accesible y su intención siguen intactos.
  • 100% Exitoso: Pasa tanto en UI v1 como en UI v2 de manera totalmente transparente.

Auto-Healing Autónomo Asistido por LLMs

El ciclo del Agente de Testing: Detección, Razonamiento, Reparación y Ejecución

1. Diagnóstico del Fallo
El script llm-healing-demo.ts intercepta el fallo en CI/CD, captura el snapshot del DOM mutado y recupera la intención de negocio original.
2. Razonamiento del LLM
El modelo analiza que el botón mutó a #act_btn_new_item_99f, pero conserva intacto el rol button y el texto "Crear Tarea".
3. Auto-Reparación (98%)
Propone automáticamente el selector semántico:
page.getByRole('button', { name: /Crear Tarea/i })
y re-ejecuta el test dejándolo 100% en verde.
